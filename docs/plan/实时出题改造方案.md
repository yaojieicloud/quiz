# 实时出题改造方案（LLM 按需生成 + 题库保底）

> 状态：**待确认**（方案讨论稿）
> 日期：2026-08-09
> 关联文档：[未来规划.md](./未来规划.md)（附件，后续功能规划）

---

## 1. 背景与动机

当前系统采用**预置题库**模式：约 1250 题（Python 理论 1000 + 实操 200 + 数学 50）预先准备并存入 `question` 表，组卷时随机抽取。

预置题库的问题：

1. **维护成本高**：出题、校验 JSON 格式、转义修复、去重、灌库，每一轮都是体力活。
2. **题目会被刷完**：高频使用下重复率上升，需要不断补充。
3. **课程与题目耦合**：改章节内容时题目不自动跟随。

**新方案核心思路**：课程定义为源，题目按需生成。维护对象从"上千道题"变成"一份课程表"。

---

## 2. 方案总览

| 维度 | 现状 | 新方案 |
|---|---|---|
| 题目来源 | 预置题库，组卷时随机抽取 | 组卷时由 LLM 按课程实时生成 |
| question 表角色 | 题库（源数据） | 已生成题目的记录（提交后落库） |
| 维护对象 | 题目 CRUD + 导入脚本 | curriculum 课程表 + 出题 prompt 模板 |
| 题目重复 | 需去重逻辑 | 天然不重复 |
| LLM 不可用时 | — | **降级**：从已落库题目随机抽取（现有机制保底） |

**一句话**：实时生成是主路径，题库是降级路径；现有 1250 题全部保留，作为保底池。

---

## 3. 已确认的设计决策

讨论中已与用户对齐的结论：

1. **curriculum 表驱动出题**：DB 中一张课程表，每次出题前抽取对应行，组合成 prompt 发给 LLM。
2. **生成题目落库**：学生提交后，本次生成的题目写入 `question` 表。LLM 掉线时组卷直接走现有的"库内随机抽题"逻辑，零改动保底。
3. **code 题流程**：生成 → 沙箱实跑参考代码算出 `expected_output` → 下发给学生。
4. **现有 1250 题保留**，不删除，作为保底池。
5. **每科目组卷规格**（延续现有约定）：
   - Python 实操：**一次 1 题**（code 类型）
   - Python 理论：一次混合 **50 题**（choice/judge/calc）
   - 数学等其他科目：同样即时生成

## 4. 详细设计

### 4.1 curriculum 表（新增）

```sql
CREATE TABLE curriculum (
    id INTEGER PRIMARY KEY,
    subject_id INTEGER NOT NULL REFERENCES subject(id),
    topic_id INTEGER REFERENCES topic(id),       -- 可空，空则为科目级通用规则
    knowledge_point TEXT NOT NULL,                -- 知识点描述（出题依据）
    question_types TEXT NOT NULL,                 -- 允许题型，如 "choice,judge,calc"
    difficulty TEXT DEFAULT 'medium',             -- easy/medium/hard
    rules TEXT,                                   -- 附加出题规则（人教版对齐、陷阱要求等）
    priority INTEGER DEFAULT 0,
    enabled INTEGER DEFAULT 1
);
```

出题时：按 `subject_id + topic_id + enabled=1` 抽行 → 拼入 prompt 模板。

### 4.2 出题服务（新增 `core/question_generator.py`）

职责：

1. 读取 curriculum 行 + prompt 模板（含题型要求、JSON 输出格式约束、示例）。
2. 调用 LLM（阿里云百炼，flash 档模型，temperature 适中）。
3. 解析返回的 JSON，做格式校验（answer 必须为字符串、选项完整等，复用 README §8 出题规范的校验规则）。
4. **choice/judge/calc**：直接返回。
5. **code 题**：先调用现有 `core/code_runner.py` 沙箱实跑参考代码 → 得到 `expected_output` → 一并返回。
6. 任何环节失败 → 抛异常，由组卷接口捕获并走降级。

### 4.3 组卷接口改造（`routers/exam.py`）

组卷流程变为：

```
start exam
  ├─ 尝试：question_generator 实时生成 N 题
  │     成功 → 题目暂存（本次试卷），返回
  └─ 失败（LLM 超时/掉线/格式错误重试仍失败）
        → 降级：从 question 表按现有逻辑随机抽 N 题（保底池含现有 1250 题 + 历史已落库生成题）
```

- 前端 `home.html` 组卷按钮需加 loading 状态（50 题生成约 20~40 秒），文案提示"AI 正在出题…"。
- 生成失败降级时前端无需感知（或仅提示"本次使用题库抽题"）。

### 4.4 提交与落库

- 提交判分逻辑**不变**（choice/judge/calc 规则判分；code 沙箱实跑 + LLM 评星）。
- 提交时将本次生成的题目写入 `question` 表（标记 `source='generated'`，建议加列区分人工题与生成题）。
- 错题本、记录、统计、学情分析逻辑全部不变。

### 4.5 数据模型改动汇总

| 改动 | 内容 |
|---|---|
| 新增表 | `curriculum` |
| `question` 加列 | `source TEXT DEFAULT 'manual'`（manual/generated） |
| 删除 | 无（现有表结构不动） |

DB 变更走 `POST /api/admin/exec-sql`（接口自动 VACUUM 备份）。

## 5. Token 成本测算

用户套餐：阿里云百炼 Token Plan **Standard（139 元/月）**：10,000 Credits/7天 + 3,000 Credits/5小时。

Credits 换算公式（官方）：`Credits = Token用量(百万) × 模型单价(元/百万) × 100`，即 1 Credit ≈ 0.01 元用量。不同模型差价大：Flash ~1000 tokens/Credit，Plus ~500，Max ~200。

### 用量假设

- 2 名学员；暑假每人每天 300 题（理论约 200 + 实操 50 + 数学 50），共 30 天。
- 开学后仅周末做题，每人每天 100 题，每月约 8 天。
- 理论/数学批量生成（一次 50 题一次调用），实操一次 1 题。
- 评分仅 code 题调 LLM，客观题规则判分 0 token。

### 测算结果（flash 档模型）

| 场景 | 月 token 总量 | 月 Credits | 占套餐比例 |
|---|---|---|---|
| 暑假（600 题/天） | ~1,100 万 | **约 700** | 7 天额度的 ~7% |
| 开学后（周末 100 题/人） | ~150 万 | **约 100** | 可忽略 |

即使改用 Plus 档模型出题（单价约 3 倍），暑假约 2,000 Credits/月，仍在套餐范围内。

**结论：token 层面无障碍。** 真正的额度约束是出题与日常 coding 共用同一 Credits 池；出题单次调用仅几 Credits，不会触碰 3,000 Credits/5小时 峰值。

### 降本选项（如需）

1. code 题评分先走 stdout 精确匹配，仅匹配失败才调 LLM（评分 token 省 60%+）。
2. 利用百炼 context caching 降低重复 prompt 的输入成本。

## 6. 实施步骤

| 阶段 | 内容 | 依赖 |
|---|---|---|
| 1 | DB 变更：建 `curriculum` 表、`question` 加 `source` 列（exec-sql） | 无 |
| 2 | 编写 curriculum 数据（三个科目的知识点 + 题型规则），导入 | 阶段 1 |
| 3 | `core/question_generator.py`：prompt 模板 + 生成 + JSON 校验 + code 题 expected_output 实跑 | 阶段 1 |
| 4 | `routers/exam.py` 组卷改造：生成主路径 + 题库降级 | 阶段 3 |
| 5 | 提交落库（生成题写入 question 表，source='generated'） | 阶段 4 |
| 6 | 前端 `home.html` 组卷 loading 状态 | 阶段 4 |

> 注意：出题 prompt 模板与校验规则是质量关键，阶段 3 完成后先人工抽样审核几批生成题的正确性，再放开使用。

## 7. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| LLM 生成答案有误 | 客观题判分错误 | 校验环节：choice 答案必须在选项内；code 题实跑验证；抽样人工审核；错题可由 admin 后台修改 |
| 生成延迟（20~40 秒） | 学生等待 | 前端 loading 文案；理论题可后台预生成缓存 |
| LLM 掉线/超时 | 无法组卷 | 自动降级到题库随机抽题（现有机制） |
| 难度/风格波动 | 不同批次不一致 | curriculum 行写精确（知识点、难度、规则），prompt 模板固定示例 |
| Credits 超额 | 出题失败 | 出题量占套餐 <10%；设置用量提醒；降级机制兜底 |
