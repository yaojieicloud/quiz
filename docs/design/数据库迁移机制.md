# 数据库迁移机制 设计文档

> 模块：`src/migrations/__init__.py`、`src/migrations/_template.py`、`src/main.py`（启动调用 `run_migrations`）、`models.py`
> 关联：[部署与运维](部署与运维.md)（本地/ECS 部署、运维 API）、[系统架构总览](系统架构总览.md)（常量速查）

---

## 1. 背景：为什么需要迁移

`src/main.py` 启动只跑 `Base.metadata.create_all(bind=engine)`。它**只建不升级**：表一旦存在，后续在 `models.py` 里新增的列、索引都不会落到已存在的库上（仅对全新表生效）。

过去加字段靠两种脆弱手段：

- **删库重建**：数据全丢，只能用于开发库；
- **手写散落 `ALTER`**：散落在 `src/data/*_fix_*.py`、甚至直接调 `exec-sql` API，没有版本记录、本地与 ECS 各跑各的，库结构逐渐不可追溯、不可重放。

掌握度这类新表越来越多后，这种"凭记忆手敲 SQL"的方式会越来越脆。本机制用一张版本表 + 编号迁移文件，把 schema 演进变成**可追溯、跨环境一致、可重复执行**的历史。

> 选型说明：未引入 DuckDB 或 Alembic。DuckDB 是 OLAP 分析型引擎，不适合本系统的事务型 CRUD 主库；Alembic 对当前体量偏重。本项目采用零依赖的自写轻量迁移器。

---

## 2. 机制总览

- 一张 `schema_migrations(version TEXT PK, applied_at TEXT)` 元数据表，记录已执行的迁移版本。
- `src/migrations/` 下每个 `.py` 文件是一个迁移，文件名以序号开头（如 `0001_xxx.py`）；`_template.py` 与 `__init__.py` 不会被加载。
- 应用启动时（`main.py` 的 `create_all()` 之后）自动调用 `run_migrations()`：扫描目录 → 跳过已执行 → 按顺序执行未应用的 `up(engine)` → 登记版本。
- 已执行的迁移**绝不会重复执行**，可安全多次重启、跨环境重放。

执行顺序（见 `src/main.py`）：

```python
Base.metadata.create_all(bind=engine)   # 首次建全表结构
from migrations import run_migrations
run_migrations()                        # 为已存在的老库补齐增量字段
```

## 3. 迁移文件格式

新建 `src/migrations/0002_xxx.py`：

```python
MIGRATION_ID = "0002_xxx"   # 唯一，建议与文件名一致

def up(engine):
    from migrations import add_column
    # 幂等加列：列已存在会自动跳过，返回是否真的加了
    add_column(engine, "questions", "hot", "INTEGER", default=0)
```

可用辅助函数（见 `src/migrations/__init__.py`）：

| 函数 | 作用 | 幂等性 |
|---|---|---|
| `add_column(engine, table, column, coltype, default=None)` | 加列（可带默认值的 `DEFAULT` 子句） | 列已存在则跳过，返回 bool |
| `create_index(engine, name, table, columns, unique=False)` | 建索引（`columns` 形如 `"a, b"`） | 索引已存在则跳过，返回 bool |
| `column_exists(engine, table, column)` | 查列是否存在 | — |
| `table_exists(engine, table)` | 查表是否存在 | — |

`up()` **必须幂等**：先查后改，保证同一迁移在全新库、已有列的老库、重复执行时结果一致。

## 4. 加字段的标准流程

1. 在 `models.py` 补该列的 ORM 声明（让 `create_all` 对新库完整、代码层类型正确）。
2. 在 `src/migrations/` 新建 `00xx_xxx.py`，写 `MIGRATION_ID` + 幂等 `up(engine)`（用 `add_column` 等辅助）。
3. 部署/重启后，`run_migrations()` 自动为**已存在的库**补齐该列；全新库由 `create_all` 直接建全结构。
4. 禁止再手写散落 `ALTER`、禁止直接调 `exec-sql` 加列（`exec-sql` 仅作应急）。

> 注意：`create_all` 与迁移是互补而非替代。`create_all` 负责"首次建全表"，迁移负责"给老库增量加字段"。二者都需与 `models.py` 保持同步——忘了写迁移，老库运行时会因 `SELECT` 缺失列而报 `no such column`。

---

## 5. 与其他机制的关系

- **与 `create_all`**：启动顺序 `create_all()` → `run_migrations()`。前者保证表存在，后者补齐增量列。
- **新增整表（非加列）**：直接在 `models.py` 声明 `Base` 子类，`create_all` 自动建表，无需迁移文件；老库数据回填用独立脚本。例：`student_mastery`（掌握度持久化表）由 `scripts/mastery_backfill.py` `create_all(tables=[StudentMastery.__table__])` 建表 + 清空重算回填（幂等）。
- **与 `exec-sql` 运维 API**：`exec-sql` 仍保留作应急，但常规加字段应走迁移文件，使版本可追溯、跨环境一致。
- **与 `seed_reward.py`**：种子数据走"存在则跳过"的幂等逻辑（2026-08-21 起 `subject_points` 覆盖改为仅首次创建、已存在不覆盖），与迁移互不冲突。
- **与历史 `src/data/*_fix_*.py`**：旧的散落 ALTER 脚本维持原样不动（本次未归拢），今后新增变更一律走迁移目录。

---

## 6. 故障与回滚

- 本机制只增不改（不含 downgrade）：如需回退某列，新增一个反向迁移（`000x_drop_xxx.py` 调 `DROP COLUMN`，SQLite 3.35+ 支持）或手写 `exec-sql`。
- 单条迁移失败：已执行的前置迁移已登记，重启会**从失败处之后**继续，不会重跑已成功的。
- 查执行进度：`SELECT * FROM schema_migrations;`（可走 `exec-sql` 或 `fetch_db.py`）。
